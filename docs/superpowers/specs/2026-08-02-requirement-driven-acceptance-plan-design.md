# 需求驱动的语义验收计划设计

## 目标

VibeVerify 根据用户提交的验收需求生成可审计的浏览器验收计划，而不是套用项目示例。Railway Worker 只在临时项目启动的 localhost 页面执行受限语义操作；报告只陈述实际执行的步骤和证据。

## 不在范围内

- 不让模型生成或执行 CSS 选择器、XPath、JavaScript、Shell 命令。
- 不执行登录、支付、删除、外部跳转、文件上传或任何会产生外部副作用的操作。
- 不因模型无法理解需求而编造检查项、默认任务名或断言结果。

## 数据流

```text
用户验收需求
  -> 测试计划生成器
  -> 语义步骤（criterion + action + assertions）
  -> Worker 白名单编译器
  -> 顺序 Playwright 执行
  -> 步骤证据
  -> 报告模型生成结论和修复提示词
  -> Worker 用步骤证据覆盖报告中的验收结果
```

## 验收计划合同

每一项计划必须保留用户可读的验收标准，并只使用下列操作：

| 操作 | 必填字段 | 执行方式 |
| --- | --- | --- |
| `assert_text_visible` | `text` | 断言页面文本可见 |
| `fill_input` | `placeholder`, `value` | 按输入框提示文字填入值 |
| `click_button` | `name` | 按按钮可访问名称点击 |
| `check_checkbox` | `name` | 按复选框可访问名称勾选 |
| `assert_text_hidden` | `text` | 断言页面文本不可见 |

一项验收标准由一组顺序操作组成，包含：

```ts
type AcceptanceCriterion = {
  id: string;
  title: string;               // 来自用户需求的可读标准
  sourceRequirement: string;   // 对应原始需求片段
  steps: SemanticStep[];
};
```

每个 `SemanticStep` 只含上述白名单动作及其字符串参数，不能持有选择器、代码、URL、命令或跨站地址。

## 计划生成与失败策略

1. 模型读取用户需求，输出结构化验收标准和语义步骤。
2. Worker 使用 Zod 校验，失败时带校验错误重试一次。
3. 第二次失败时：
   - 仅保留“首页可访问、控制台摘要”等通用运行证据；
   - 将无法转换的原始需求写为 `manual_review`，状态为“待人工补充”，不是“未验证”或“功能失败”；
   - 不生成任何具体点击、填值、勾选或筛选操作。
4. 若计划包含禁用动作、未知动作或超过步骤上限，则拒绝该项并写入 `manual_review`。

## 执行与证据

- 所有步骤在同一个浏览器会话中按计划顺序执行；不得 `Promise.all` 并发改变页面状态。
- 每项验收标准拥有独立证据 ID，并记录：原始需求、实际动作摘要、断言、状态、错误代码和截图/控制台摘要引用。
- 一项中的任一步失败，只令该项为 `not_verified`；其后的独立项继续执行。
- 必须在执行前后保持 localhost 边界；禁止访问非本地 URL。

## 报告呈现

“功能验收明细”按三组展示：

1. **已验证**：所有步骤实际执行且断言通过。
2. **未验证**：步骤实际执行，但任一动作或断言失败；展示失败步骤。
3. **待人工补充**：需求无法安全转换为白名单步骤；展示原始需求和缺少的可观察条件，不把它计为功能失败。

每项展示“验收标准、执行动作、预期结果、实际结果、证据”。报告模型只负责结论、问题说明和修复提示词；Worker 的步骤状态和证据为最终事实来源。

## MVP 支持范围

首期支持静态文本、按钮点击、输入填值、复选框勾选及文本显示/隐藏断言，面向无需认证的本地 Web 页面。筛选、表单和列表等交互由这些基础操作组合表达，不再有“任务清单”专用硬编码流程。

## 验证标准

- 用两份不同文案的任务清单需求验证：计划中的填充值、按钮名、断言文本来自各自需求，而非固定示例词。
- 用包含不支持操作的需求验证：它进入“待人工补充”，Worker 不点击任何危险动作。
- 用状态依赖步骤验证：第二步在第一步完成后才启动。
- 用报告测试验证：报告的验收状态与 Worker 保存的步骤证据一一对应。
