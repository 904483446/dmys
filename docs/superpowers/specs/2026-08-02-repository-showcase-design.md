# VibeVerify GitHub 仓库展示设计

## 目标

将 VibeVerify 的 GitHub 首页从过期的 Phase 0 工程说明，升级为面向产品、招聘和作品集读者的可信产品展示页；让读者在两分钟内理解产品解决的问题、真实实现边界和当前验证状态。

## 读者与成功标准

主要读者是招聘方、产品/工程协作者和潜在试用者，而不是首次部署项目的开源贡献者。成功标准：

- 首屏说明 VibeVerify 服务的对象、问题和交付物。
- 读者可以顺着“需求 → Worker 执行 → 真实证据 → 报告/修复提示词”理解产品链路。
- README 明确 Web/Vercel 不执行用户代码，Railway Worker 才执行受限验收步骤。
- 已验证的本地/CI/Web 构建与尚未完成的 Railway/生产单次验收分开陈述，不能把预览部署或测试结果写成生产验收成功。
- 文档链接、快速启动和贡献入口仍然可供开发者继续使用，但不抢占首屏叙事。

## 方案比较

### 方案 A：产品优先、证据支撑（采用）

README 先呈现定位、使用流程、可信边界和当前状态；安装与贡献信息放在后半部分。它能表达产品价值，同时保持对实现和部署状态的诚实。

### 方案 B：工程文档优先

以环境、命令和模块为首页主体。对维护者友好，但不能有效说明 VibeVerify 作为验收产品的差异。

### 方案 C：营销落地页优先

以大幅宣传文案和视觉效果为主。短期更醒目，但容易与未完成的生产验收脱节，因此不采用。

## README 信息架构

1. **定位与价值**：面向非技术 Vibe Coding 用户的私有 Web 功能验收平台；产出可审计的验收报告和可复制的修复提示词。
2. **工作方式**：以四步 Mermaid 图解释用户需求、受限语义计划、Railway Worker 本地执行、报告呈现的路径。
3. **可信边界**：列出 Web/Vercel、Railway Worker、模型和人工补充的职责；禁止把不能自动转换的需求写成已验证。
4. **当前能力与验证状态**：使用表格分离代码/本地质量门禁、Vercel 部署、Railway Worker 和生产验收；仅写有证据支持的状态。
5. **项目结构与文档导航**：保留到系统架构、AI 设计、部署 Runbook 等的入口。
6. **本地启动与质量命令**：最小可复制的安装、lint、typecheck、test 命令；不写真实环境变量值。
7. **贡献和安全报告入口**：链接到 GitHub Issue/PR 模板和安全边界说明。

## GitHub 基础文件

- `.github/ISSUE_TEMPLATE/bug_report.yml`：引导用户提供验收需求、实际结果、期望结果、脱敏日志和复现步骤；禁止提交密钥、Token、Cookie、原始私有源码。
- `.github/ISSUE_TEMPLATE/feature_request.yml`：收集用户目标、验收标准、风险与替代方案。
- `.github/pull_request_template.md`：要求说明用户价值、测试证据、部署影响与未验证项目。
- `CONTRIBUTING.md`：说明分支、质量门禁、提交范围和 Worker-only 执行边界。

本轮不新增 `SECURITY.md`：仓库尚未确认私密漏洞报告渠道，不能虚构邮箱或公开提交地址。安全问题的公开报告入口会在确认渠道后单独设计。

## 视觉与素材

不添加演示录屏、假数据截图或伪造生产验收标记。README 预留“真实脱敏截图”区域，只有在取得真实页面截图后再插入；在此之前使用 Mermaid 流程图和文本说明。

## 非目标

- 不修改产品代码、数据库、部署配置或 CI 工作流。
- 不部署 Vercel/Railway，不创建生产验收任务。
- 不创建 GitHub Release、徽章墙或第三方分析追踪。

## 验证

- Markdown 链接指向存在的文件。
- README 不保留“仅完成 Phase 0”等过期表述。
- `git diff --check` 通过。
- 仅文档和 GitHub 模板改动，不需要声称产品端到端验收完成。
