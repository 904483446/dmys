# 【需要确认名称】VibeVerify 产品需求文档（PRD）

## 产品概述

### 背景与定位

`VibeVerify` 为工作名称，尚待最终确认；其余产品需求不依赖名称。

Vibe Coding 用户常可借助 AI 快速产出 Web 项目，却缺乏判断“功能是否按需求完成”的方法。VibeVerify 是一个私有的功能验收助手：以用户目标为主依据，以可选 PRD 和实际运行证据为补充，给出可解释的验收建议，而不是替代用户做产品决策。

### 用户画像与场景

- 非技术创作者：用 Cursor、OpenHands、Claude Code 等产出网站，想在交付前检查。
- 独立开发者/产品经理：希望把需求与真实浏览器行为对照，定位失败功能。
- 使用场景：本地项目未推送时上传 ZIP；已在 GitHub 的项目通过私有/公开仓库导入；修复后发起重新验收并比对历史。

### 核心价值

无需理解测试代码即可获得真实运行证据；在保留私有代码的前提下，生成适合交给 AI 编程工具修复的明确提示词。

## MVP 目标与范围

### MVP 必须实现

- 邀请制账号访问；Google、GitHub、邮箱验证码登录。
- 需求文本必填、PRD 可选；ZIP 与 GitHub App 仓库来源。
- 仅处理可独立启动的 React/Vite、Next.js 单体 Web 项目。
- Worker 完成构建、启动、Playwright 浏览器测试、证据采集和 AI 报告。
- 私有报告列表、独立详情、重新验收、PDF/Markdown 导出。

### 暂不包含

- 匿名公开注册、团队协作、公开报告链接、排行榜。
- 多服务项目、数据库/私密环境变量、移动原生应用、Python/Java 等项目。
- 主观 UI 美学评分、自动修改源码、OpenHands 自动修复。
- 强隔离多租户执行平台、无限并发或商业计费。

### 长期扩展

强隔离短生命周期 Runner、更多框架、Vercel 预览环境、私有服务密钥托管、团队空间、报告对比、OpenHands 修复任务与计费。

## 功能需求

### 1. 用户与访问控制

**流程**：用户登录后，首次创建任务时输入统一内测码；验证成功后账号获得内测访问权限并进入“我的报告”。未验证用户看到“当前为邀请测试阶段”与输入入口。

**输入/输出**：OAuth 回调或邮箱 OTP；首次访问时可输入内测码；输出会话与个人资料。

**业务规则**：所有用户数据均以 `user_id` 归属；用户只能读取、导出或删除自己的任务和报告。内测码只在服务端环境变量中保存和比对，验证成功后仅记录 `access_status = active`，不保存明文内测码。

**异常**：失效邀请、OAuth 拒绝、OTP 过期时给出中文可行动提示，不泄露内部错误。

**验收**：不同用户不能通过 URL 或 API 读取彼此资源；登录后首次访问显示空状态和“新建验收”。

### 2. GitHub 连接与项目导入

**流程**：用户可安装 GitHub App 并选择授权仓库；新建任务时选分支/提交。也可上传 ZIP。

**输入**：GitHub repository/ref 或 `.zip`（最大 50MB）。需求文本必填；PRD 可选。

**业务规则**：GitHub App 只申请所选仓库的 Contents read-only 权限；ZIP 在上传前校验大小、扩展名和压缩炸弹风险；禁止 `.env`、`.git`、`node_modules` 进入执行上下文。

**输出**：创建 `queued` 状态的验收任务。

**异常/验收**：未授权仓库不可选择；无效 ZIP、超大文件、缺失需求必须在提交前阻止；私有仓库不会在报告或日志中展示 URL/Token。

### 3. 创建与执行验收任务

**流程**：提交后跳转“我的报告”，显示 `queued → preparing → building → running → testing → reporting → completed/failed`。

**规则**：每用户每日最多 3 个任务、单任务最多 10 分钟、同一用户同时只运行 1 个任务。Worker 自动识别 `package.json` 与支持的启动脚本；无法识别或构建失败也必须生成失败报告。

**异常/验收**：任务超时、依赖安装失败、端口无法监听、浏览器崩溃须记录规范错误码与可读摘要；用户刷新后仍能看到最新状态。

### 4. AI 驱动验收与报告

**流程**：系统以需求为主、PRD 为辅助、项目结构/运行证据为佐证，生成内部测试意图；Playwright 执行；AI 把证据整理为报告。

**输出**：结论（`passed`、`at_risk`、`failed`）、0–100 分、置信度、已验证功能、问题列表、证据、修复提示词。

**判定规则**：无法启动、核心流程失败、严重运行错误为不通过；非核心问题或需求模糊为有风险；未发现阻断问题才可通过。报告必须声明“自动验收建议，最终由用户判断”。

**验收**：每个问题包含影响等级、复现步骤或证据、建议；AI 不得声称没有被浏览器执行或运行日志支持的事实。

### 5. 我的报告与报告详情

**流程**：统一列表置顶进行中任务，历史报告按最新排序；列表仅展示项目、时间、结论、分数、问题数量。点击后进入 `/reports/{id}` 独立详情；可返回原筛选状态。

**详情**：展示结论、分数、需求摘要、证据截图、问题、可复制修复提示词、导出、重新验收。

**验收**：报告仅本人可访问；重新验收保留原报告、复用需求/PRD，并创建新的不可变报告版本。

## 非功能要求

- 中文优先；用户可输入英文需求；README 提供中英文摘要。
- 首页内嵌固定演示报告，不包含真实用户数据。
- 原始源码、解压目录、临时容器在任务结束后删除；报告数据默认长期保留直到用户删除。
- API 统一错误结构：`{ error: { code, message, details? } }`，message 为中文。
